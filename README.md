# Date Planner

Date Planner — веб-сервис для создания персональных приглашений на свидание и последующего совместного планирования. Сейчас проект поддерживает быстрый опубликованный сценарий, защищённые черновики расширенного режима, персональную интерактивную страницу для получателя, секретную ссылку автора, два сценария подготовки двух–пяти вариантов даты и полный выбор из трёх–шести вариантов активности.

## Стек

- **Frontend:** Vue 3, Nuxt, TypeScript, Composition API, ESLint и Vitest.
- **Backend:** Python, Django, Django REST Framework, PostgreSQL, django-cors-headers, drf-spectacular, pytest и Ruff.
- **Инфраструктура:** Docker, Docker Compose, GitHub Actions и конфигурация через переменные окружения.

## Требования

Для рекомендуемого локального запуска нужны только:

- Docker Engine с плагином Compose v2;
- Git;
- свободные порты `3000` и `8000`.

При работе через Docker Compose устанавливать Python, Node.js и PostgreSQL на хост не требуется.

## Первый запуск

Создайте локальный файл окружения из безопасного шаблона:

```bash
cp .env.example .env
```

Значения из `.env.example` предназначены только для локальной разработки. Для любого другого окружения обязательно замените секретный ключ и пароль базы данных.

Соберите и запустите все сервисы:

```bash
docker compose up --build
```

Backend дождётся готовности PostgreSQL и автоматически применит миграции. После добавления новой миграции её также можно применить вручную:

```bash
make migrate
```

Остановить стек можно командой `make down`. Данные PostgreSQL сохраняются в именованном томе `postgres_data`.

## API приглашений

Создать приглашение можно публичным запросом:

```bash
curl -X POST http://localhost:8000/api/v1/invitations/ \
  -H 'Content-Type: application/json' \
  -d '{
    "author_name": "Алиса",
    "recipient_name": "Борис",
    "message": "Давай сходим на свидание?",
    "creation_mode": "quick"
  }'
```

Поле `message` необязательно: его можно не передавать или отправить пустой строкой. Имена автора и получателя остаются обязательными. Поле `creation_mode` принимает `quick` или `extended`; если его не передать, backend сохранит `quick`.

Быстрый режим создаёт приглашение сразу со статусом `published` и заполняет `published_at`. Расширенный режим создаёт защищённый `draft`: management-ссылка работает сразу, а публичное чтение, ответ получателя и выбор варианта возвращают `404` до явной публикации.

Ответ содержит непредсказуемый UUID и `management_token`. Открытый токен возвращается только при создании: сервер сохраняет только его SHA-256-хеш. Сохраните сформированную frontend секретную ссылку автора — восстановить её позднее без аккаунта нельзя.

Получить публичные данные опубликованного приглашения можно по адресу:

```text
GET /api/v1/invitations/<uuid>/
```

Черновик остаётся доступен только автору через management endpoint. Опубликовать его можно идемпотентным запросом:

```http
PUT /api/v1/invitations/<uuid>/publish/
Authorization: Bearer <management-token>
```

Первый успешный запрос переводит приглашение в `published` и устанавливает `published_at`. Повторный `PUT` возвращает то же состояние и не меняет время публикации.

Получатель сохраняет свой ответ через публичную ссылку-возможность:

```http
PUT /api/v1/invitations/<uuid>/response/
Content-Type: application/json

{"response_status": "accepted"}
```

Допустимые ответы — `accepted` и `declined`. Повторный `PUT` позволяет изменить решение; `responded_at` хранит время последнего изменения ответа. Начальное состояние нового приглашения — `pending`.

Данные для страницы автора доступны по отдельному endpoint только с выданным токеном:

```text
GET /api/v1/invitations/<uuid>/manage/
Authorization: Bearer <management-token>
```

Тот же endpoint принимает частичное редактирование безопасных полей:

```http
PATCH /api/v1/invitations/<uuid>/manage/
Authorization: Bearer <management-token>
Content-Type: application/json

{
  "recipient_name": "Галина",
  "message": "Пойдём в театр?",
  "creation_mode": "extended",
  "planning_mode": "before_acceptance"
}
```

Редактировать можно только `author_name`, `recipient_name`, `message`, `creation_mode` и `planning_mode`. Режим планирования принимает `before_acceptance` или `after_acceptance`: быстрые приглашения всегда используют `after_acceptance`, а предварительная подготовка доступна только расширенному черновику. После публикации изменить `planning_mode` нельзя. Переключение черновика с `before_acceptance` на `after_acceptance` удаляет подготовленные варианты, чтобы скрытый набор не перешёл в другой сценарий. Lifecycle-поля, management-токен и ответ получателя отклоняются с `400 Bad Request`, а не игнорируются. Пустой `PATCH` и повтор запроса с теми же нормализованными значениями идемпотентны и не меняют `updated_at`. Изменение черновика не публикует его; изменения опубликованного приглашения сразу видны по публичной ссылке.

Расширенное приглашение получает пять серверных конфигураций экранов: `invitation`, `acceptance`, `date_selection`, `activity_selection` и `final`. Получить их в стабильном порядке можно только с management-токеном:

```http
GET /api/v1/invitations/<uuid>/screens/
Authorization: Bearer <management-token>
```

Ответ содержит только содержимое экрана: `screen_type`, `title`, `subtitle`, `button_text`, `secondary_button_text`, `image_key` и `template_text`. Поле `template_text` заполнено только у финального экрана; для остальных экранов база данных требует пустое значение. Внутренние UUID и временные метки строк не раскрываются. Быстрые приглашения не создают этот набор и возвращают `409 Conflict` для screen endpoint. При переключении приглашения в расширенный режим недостающие конфигурации создаются идемпотентно.

Основной экран расширенного черновика можно частично обновить через `PATCH /api/v1/invitations/<uuid>/screens/invitation/`. Экран после согласия редактируется отдельно через `PATCH /api/v1/invitations/<uuid>/screens/acceptance/`. Оба endpoint требуют management-токен, принимают только разрешённые тексты и совместимый ключ встроенного изображения, не обновляют временную метку при пустом или идентичном повторе и закрываются после публикации. Поле `secondary_button_text` доступно только первому экрану, поскольку экран после ответа «Да» содержит одну кнопку продолжения.

Финальный экран хранит безопасный текстовый шаблон. На этапе DPL-501 отдельно редактируется только он:

```http
PATCH /api/v1/invitations/<uuid>/screens/final/
Authorization: Bearer <management-token>
Content-Type: application/json

{
  "template_text": "{recipient}, жду тебя {date} в {time}. Встречаемся в {place}, а дальше нас ждёт {activity} 💘"
}
```

Разрешены только переменные `{author}`, `{recipient}`, `{date}`, `{time}`, `{place}` и `{activity}`. Они заменяются обычным текстом. Обращение к атрибутам или индексам, преобразования, спецификации форматирования, неизвестные переменные и незакрытые фигурные скобки возвращают `400 Bad Request`. Литеральные скобки записываются как `{{` и `}}`. Пустой или идентичный `PATCH` не меняет `updated_at`; после публикации шаблон замораживается вместе с остальной конфигурацией экрана.

Автор сохраняет от двух до пяти вариантов свидания через один endpoint. В режиме `before_acceptance` редактор доступен на втором шаге расширенного конструктора до публикации; в режиме `after_acceptance` тот же редактор появляется на management-странице только после ответа «Да»:

```http
PUT /api/v1/invitations/<uuid>/plan-options/
Authorization: Bearer <management-token>
Content-Type: application/json

{
  "options": [
    {
      "starts_at": "2026-08-01T18:30:00+07:00",
      "place": "Кофейня у парка",
      "comment": "Столик у окна"
    },
    {
      "starts_at": "2026-08-02T16:00:00+07:00",
      "place": "Набережная",
      "comment": ""
    }
  ]
}
```

Дата должна быть в будущем и содержать явное смещение часового пояса, место обязательно, а комментарий варианта можно оставить пустым. Порядок элементов массива становится порядком отображения вариантов. Редактор конструктора показывает часовой пояс браузера, позволяет менять порядок, сохраняет только реальные введённые значения и передаёт локальный черновик в мобильный preview без отдельного API-запроса.

Для `before_acceptance` публикация разрешена только при наличии двух–пяти будущих вариантов. До ответа получателя публичный API скрывает подготовленный набор; после `accepted` варианты становятся доступны для выбора. Опубликованный предварительный набор нельзя заменять в обычном состоянии. Единственное исключение — выбранный, но не подтверждённый вариант уже прошёл: тогда автор может атомарно заменить весь набор будущими вариантами, прежний выбор сбрасывается, а режим и публикация приглашения сохраняются. Для `after_acceptance` действует тот же recovery-контракт: после согласия набор можно менять, пока нет будущего или подтверждённого выбора, а истёкший неподтверждённый выбор разрешает безопасную замену.

Получатель выбирает один из предложенных вариантов через публичную ссылку:

```http
PUT /api/v1/invitations/<uuid>/selection/
Content-Type: application/json

{"option_id": "<option-uuid>"}
```

Повтор того же выбора идемпотентен, а до итогового подтверждения получатель может выбрать другой вариант.
Публичный сценарий после ответа «Да» использует сохранённую конфигурацию `date_selection`: заголовок, подзаголовок, текст основной кнопки и совместимое локальное изображение. Интерфейс показывает только варианты, которые остаются будущими относительно `server_now`, сохраняет порядок автора и отдельно объясняет состояния, когда автор ещё не добавил даты или все предложения уже прошли. Сохранённый вариант помечается как текущий, но до итогового подтверждения получатель может выбрать и сохранить другой актуальный вариант.

Автор фиксирует выбранный план отдельным необратимым запросом:

```http
PUT /api/v1/invitations/<uuid>/confirmation/
Authorization: Bearer <management-token>
Content-Type: application/json

{"confirmed": true, "option_id": "<selected-option-uuid>"}
```

Подтвердить можно только принятый, выбранный и ещё не наступивший вариант. UUID в запросе должен совпадать с вариантом, который видел автор: если получатель успел изменить выбор, сервер ничего не фиксирует и предлагает обновить данные. Повтор подтверждения того же варианта безопасен и не меняет временные метки. После него нельзя отклонить приглашение, выбрать другой вариант или заменить предложения; обе страницы показывают одинаковую финальную карточку плана.

Если неподтверждённый выбранный вариант успел пройти, management-страница открывает единый recovery-редактор для обоих режимов планирования. Успешная замена удаляет старые UUID вариантов и сбрасывает `selected_option_id`, `selected_at` и `confirmed_at`; публичная и management-страницы получают один и тот же новый набор. Точный повтор уже выполненной замены идемпотентен и не меняет UUID или `updated_at`. Будущий выбор и подтверждённый план остаются закрытыми от замены, а прошедшие варианты нельзя выбрать повторно. API также возвращает текущее серверное время: интерфейс сверяется с ним, поэтому неверные часы на устройстве не блокируют выбор или подтверждение.

Авторская коллекция активностей хранится отдельно от дат и экранов. Для расширенного приглашения management API позволяет прочитать сохранённые варианты и атомарно заменить весь набор из трёх–шести элементов:

```http
GET /api/v1/invitations/<uuid>/activity-options/
Authorization: Bearer <management-token>
```

```http
PUT /api/v1/invitations/<uuid>/activity-options/
Authorization: Bearer <management-token>
Content-Type: application/json

{
  "options": [
    {
      "title": "Прогулка",
      "description": "Пройтись по набережной",
      "image_key": "activity-walk",
      "place": "Набережная"
    },
    {
      "title": "Кино",
      "description": "Выбрать фильм вместе",
      "image_key": "activity-movie",
      "place": "Кинотеатр"
    },
    {
      "title": "Кофе",
      "description": "Посидеть в уютной кофейне",
      "image_key": "activity-coffee",
      "place": "Кофейня"
    }
  ]
}
```

Порядок массива становится `position` от `0` до `5`. В первой версии API редактируются только название, описание, локальный `image_key` и необязательное место. Модель также резервирует необязательные `estimated_price` и `external_url`, но API пока намеренно их не принимает. Точный повтор `PUT` сохраняет UUID и временные метки. Редактировать набор можно только в расширенном черновике; после публикации он остаётся доступен автору для чтения, но закрыт для изменения. Quick-приглашения не получают этот ресурс. Третий шаг конструктора переиспользует этот контракт и показывает локальные несохранённые варианты в мобильном preview.


После принятия расширенного приглашения и сохранения даты публичный сценарий показывает экран `activity_selection` и упорядоченные карточки автора. Получатель сохраняет один вариант отдельным публичным запросом:

```http
PUT /api/v1/invitations/<uuid>/activity-selection/
Content-Type: application/json

{"option_id": "<activity-option-uuid>"}
```

До принятия активности скрыты. Выбор можно менять до окончательного подтверждения, точный повтор того же UUID идемпотентен, а удалённый или чужой вариант отклоняется. После финального подтверждения сохранённая активность замораживается. Если у расширенного приглашения уже есть варианты активностей, автор не может подтвердить дату, пока получатель не выберет одну из них.

Финальное подтверждение связывается с комбинацией, которую автор действительно видит на странице управления:

```http
PUT /api/v1/invitations/<uuid>/confirmation/
Authorization: Bearer <management-token>
Content-Type: application/json

{
  "confirmed": true,
  "option_id": "<date-option-uuid>",
  "activity_option_id": "<activity-option-uuid>"
}
```

Для приглашения без активностей `activity_option_id` передаётся как `null`. Backend под блокировкой приглашения повторно сверяет оба UUID с актуальным выбором. Если получатель успел поменять активность, подтверждение возвращает `409 selected_activity_changed`, поэтому устаревшая страница автора не может незаметно зафиксировать другую комбинацию. Точный повтор уже подтверждённой пары остаётся идемпотентным. До и после подтверждения дата, место, комментарий и выбранная активность отображаются одной согласованной карточкой; итоговая карточка одинакова на публичной и management-страницах.

Frontend создаёт две capability-ссылки:

- публичную `/invite/<uuid>` — она доступна только после публикации и отправляется получателю;
- секретную `/manage/<uuid>#token=<management-token>` — она работает и для черновика, и после публикации, её сохраняет автор.

Токен находится во fragment ссылки, поэтому браузер не отправляет его серверу вместе с первым HTTP-запросом. Страница считывает токен только в браузере, сразу очищает адресную строку и на время вкладки хранит его в `sessionStorage`; к API он передаётся в заголовке `Authorization`. В production обязателен HTTPS.

Каждое приглашение хранится отдельной записью, поэтому данные и ответы разных людей не перезаписывают друг друга. Публичного `GET /api/v1/invitations/` нет: API не раскрывает общий список приглашений. UUID публичной ссылки служит возможностью прочитать приглашение и отправить ответ, а отдельный management-токен — посмотреть данные и текущий статус на странице автора. Существующие до миграции management-токена записи остаются доступными только по публичной ссылке; при необходимости управления их следует создать заново.

Все API-запросы ограничены по частоте. По умолчанию анонимному клиенту разрешено `60` запросов в минуту, будущему авторизованному — `120`, создание приглашений дополнительно ограничено до `10` запросов в минуту с одного IP, а сохранение ответа и операции планирования — до `20` для каждого scope. При превышении сервер отвечает `429 Too Many Requests` и возвращает `Retry-After`.

В текущем Compose throttling использует общий файловый cache внутри одного backend-контейнера, поэтому лимит разделяется между Gunicorn workers. Это базовая защита от чрезмерного использования API, а не полноценная DDoS-защита. Перед горизонтальным production-развёртыванием понадобятся общий сетевой cache и rate limiting на уровне доверенного reverse proxy или API gateway.

Все команды выполняются в сервисах Docker Compose и не зависят от глобально установленных Python- или Node-пакетов.

## Тесты и проверки качества

Полный набор проверок запускается так:

```bash
make test
make lint
```

Отдельные проверки можно запустить явно:

```bash
docker compose run --rm backend pytest
docker compose run --rm backend ruff check .
docker compose run --rm frontend npm run test
docker compose run --rm frontend npm run lint
docker compose run --rm frontend npm run typecheck
docker compose run --rm frontend npm run build
```

GitHub Actions выполняет те же категории проверок backend и frontend при каждом push и pull request.

## Текущие возможности

- Адаптивная романтическая страница приглашения на локальных графических ресурсах.
- Управление ответами мышью, касанием и клавиатурой с учётом `prefers-reduced-motion`.
- Состояния принятого и отклонённого приглашения и кнопка сброса демонстрации.
- Выбор быстрого или расширенного режима создания с сохранением режима в PostgreSQL и API.
- Форма создания с клиентской и серверной валидацией, обработкой ошибок и копированием ссылок.
- Публичные персональные страницы приглашений по UUID через `/invite/<uuid>`.
- Секретные страницы автора по capability-ссылке без регистрации и пароля.
- Защищённое частичное редактирование имён, сообщения и режима с минимальным PATCH-payload, идемпотентными повторами и предупреждением о несохранённых изменениях.
- Четырёхшаговый каркас конструктора для расширенного черновика: приглашение, дата и время, активности и финал.
- Второй шаг конструктора позволяет выбрать подготовку дат заранее или после согласия; быстрый режим всегда использует сценарий после согласия.
- В режиме подготовки заранее второй шаг содержит общий редактор двух–пяти вариантов с добавлением, удалением, изменением порядка, локальной валидацией, серверными ошибками по полям и сохранением перед переходом вперёд.
- Текущий шаг конструктора синхронизируется с URL и восстанавливается в пределах вкладки через `sessionStorage`.
- Первый шаг конструктора редактирует основные данные и автоматически сохраняет минимальный PATCH после паузы во вводе.
- Расширенное приглашение получает пять уникальных конфигураций экранов с безопасными значениями по умолчанию и защищённым read-only API.
- Конструктор загружает серверный набор экранов, проверяет полноту и порядок, затем показывает подготовленные конфигурации на соответствующих шагах.
- Встроенная библиотека содержит 18 локальных SVG-иллюстраций для пяти экранов; конструктор показывает совместимые варианты и текущую иллюстрацию без обращений к сторонним CDN.
- Первый экран расширенного черновика редактируется прямо в конструкторе: заголовок, подзаголовок, обе кнопки и выбранная иллюстрация автоматически сохраняются отдельным минимальным PATCH.
- Экран после ответа «Да» настраивается независимо: автор выбирает иллюстрацию, заголовок, подзаголовок и кнопку перехода к планированию.
- Единый интерактивный мобильный предпросмотр проигрывает пять экранов получателя, сразу отражает несохранённые изменения и поддерживает размеры 320, 375 и 430 px.
- В предпросмотре можно пройти выбор даты и активности, проверить финальную карточку, вернуться назад или сбросить сценарий; на втором шаге введённые даты отражаются сразу, а демонстрационные значения не отправляются в API.
- После согласия публичная страница показывает сохранённый второй экран, а его кнопка переводит фокус к актуальному состоянию планирования с учётом `prefers-reduced-motion`.
- Автосохранение выполняет только один запрос одновременно, ставит новые изменения в очередь, поддерживает ручной повтор и принудительное сохранение перед навигацией.
- Конструктор проверяет management-токен и не открывается для быстрого режима или уже опубликованного приглашения.
- Сохранение согласия или отказа получателя с состояниями загрузки, успеха и повтора после ошибки.
- Отображение актуального ответа и времени его получения на секретной странице автора.
- Редактор двух–пяти вариантов даты, времени и места на секретной странице автора.
- Настраиваемый экран выбора даты на публичной странице: локальная иллюстрация и тексты `date_selection`, только актуальные будущие варианты, сохранение текущего выбора и возможность изменить его до подтверждения.
- Необратимое итоговое подтверждение автором и общая финальная карточка плана.
- Восстановление обоих режимов планирования после истечения выбранного, но неподтверждённого варианта с идемпотентной заменой набора.
- Модель `ActivityOption` с принадлежностью приглашению, порядком, тремя–шестью элементами в management API и атомарной идемпотентной заменой коллекции расширенного черновика.
- Третий шаг конструктора редактирует 3–6 активностей, сохраняет порядок и локальные изображения, защищает несохранённые изменения и сразу обновляет preview.
- После сохранения даты получатель видит экран выбора активности, может менять выбор до окончательного подтверждения, а автор подтверждает точную пару UUID даты и активности из единой карточки выбранного плана.
- Финальный экран использует безопасный шаблон с шестью разрешёнными переменными; backend валидирует грамматику, frontend подставляет только обычные строки, а мобильный preview показывает результат на демонстрационных или введённых данных.
- Жизненный цикл `draft` → `published` с серверным временем публикации и идемпотентным endpoint публикации.
- Расширенный режим создаёт приватный черновик; публичные recipient-endpoints скрывают его как отсутствующий.
- API создания, публикации, публичного чтения, сохранения ответа, планирования, подтверждения и защищённого чтения/редактирования автора через `/api/v1/`.
- Одноразовая выдача management-токена и хранение в базе только его хеша.
- Серверная валидация имён и текста приглашения без публичного списка записей.
- Общий и отдельные для создания, ответа и планирования rate limits с ответом `429 Too Many Requests`.
- Индикатор доступности backend, видимый только в режиме разработки.
- Health endpoint Django, OpenAPI-схема и Swagger UI.
- Локальная разработка с PostgreSQL и healthcheck сервисов.
- Автоматические линтеры, тесты, проверка типов и production-сборка frontend в CI.

## Ближайшие этапы

Следующий этап — DPL-502: добавить полноценный редактор финального экрана — изображение, заголовок, описание, безопасный шаблон и настройки отображения итоговых параметров.

Регистрация на текущем этапе не нужна: секретная management-ссылка подтверждает право просмотра страницы автора. Аккаунты стоит добавлять только тогда, когда появятся личный кабинет, восстановление доступа, список нескольких приглашений одного автора или управление ими с разных устройств. Фоновые очереди и deployment-инфраструктуру также следует добавлять по мере конкретной необходимости.
